Скопируй весь текст ниже в новый чат проекта. Он содержит контекст, цель, порядок работы и правила передачи результатов. Предыдущая переписка не нужна.

---

Ты работаешь над Maffinet Android в `E:\maffinet android`. Нужно самостоятельно переработать приложение в продукт со сценарием «выбрал установленные приложения → включил → получил автоматически настроенный обход». Первый новый чат выполняет исследование, безопасную очистку и окончательный план. Каждый последующий чат выполняет один следующий этап с проверками и фиксацией. Продолжай работу автономно в пределах текущего этапа.

## Цель и границы продукта

Сохрани принцип простоты и автоматизации, которым вдохновил NetFix. Создай собственные организацию приложения, UX, тексты, Android application layer, lifecycle и управление политиками. Изменение цвета, названий классов и добавление ещё одного переключателя не считается переработкой. Нужен самостоятельный механизм доступа для выбранных приложений.

Основной объект интерфейса — выбранное приложение и наблюдаемый результат. Пользователь не должен разбираться в DNS, Hosts, ByeDPI argv и глобальных стратегиях для обычного запуска. Для расширенной диагностики эти механизмы допустимы в инструментах, с объяснимыми настройками.

Базовый режим: один Android VpnService, только выбранные приложения, локальный DPI, контролируемый DNS и разрешённые общедоступные альтернативные endpoints. Без root, регистрации и собственного внешнего сервера. Не добавляй обязательный VPN-провайдер, облачный backend или платный аккаунт. Публичный Smart DNS может использовать внешний proxy своего провайдера; не называй такую схему отсутствием внешней инфраструктуры. Локальные методы не гарантируют устранение любой IP/GeoIP-блокировки или ограничений аккаунта.

Новый UI и продуктовые тексты должны иметь только собственную идентичность Maffinet. Сравнение с исходными проектами допустимо в research и исторической документации. Использование независимых open-source ядер допустимо напрямую, с их лицензиями. Полная замена слоя приложения должна быть доказана происхождением кода и зависимостей; не удаляй обязательную атрибуцию сохраняемого заимствованного кода и не называй переименование самостоятельной реализацией. Документируй путь удаления унаследованного application layer. Не утверждай clean-room процесс после изучения старого кода.

Если каталог недоступен, используй первичные публичные источники и явно запиши пределы сравнения. Не меняй соседний macOS-проект и не переноси его инструкции как требования Android.

Что уже сделано: собственный applicationId `io.maffinet.android`, branding, явный allowlist, независимые VPN/Telegram desired/runtime states, domain parser/import, стратегии и probes, CI/JVM/native/instrumentation проверки, targetSdk36/minSdk26, Automatic Access и отдельная DNS-диагностика. Эти результаты сохраняй как знания и regression contracts, даже при новой реализации.

Текущий путь: `VpnService → TUN → HEV tun2socks → local SOCKS → ByeDPI → Internet`. HEV поставляется как кастомные prebuilts с JNI rebind; точный source pin недоступен. Rust Telegram также имеет вопросы воспроизводимости. Это исследовательские ограничения, а не основание оставить opaque бинарники в новом целевом выпуске.

Подтверждённые ограничения, которые надо проверить в текущем коде:

1. Выбор пакетов направляет трафик в VPN, но не подбирает успешный обход сам по себе.
2. Hosts import извлекает hostname, а desktop IP mapping не применяется.
3. DNS назначается Builder, но broker/recovery до TLS нет. NXDOMAIN/timeout до соединения может не попасть в TLS observer.
4. `automatic_access.c` исключает exact-host обработку при ECH-расширении, включая возможный GREASE. Outer SNI не доказывает внутренний hostname.
5. Native recovery route storage IPv4; selective UDP forwarded unchanged; обычная TCP-проба не подтверждает QUIC/IPv6-only.
6. `HostObservation` не содержит UID/original flow tuple; нельзя обещать точную per-app диагностику по текущим данным.
7. Изученное восстановление в основном влияет на следующие соединения; реальный клиент может не повторить первый запрос.
8. Успех анонимного GET `/` и префикса тела не доказывает API/авторизацию/медиа выбранного приложения.

Записанный физический пример: OnePlus CPH2747, Android16, 0.3.2-alpha. Auto-проба LinkedIn с обычным SNI получила HTTP200 и полный ответ, но само приложение после холодного старта не загрузило ленту; наблюдалось ECH-расширение, которое исключается из маршрутизации. Ручной режим 0.3.1 в той же сессии загрузил ленту. Это не доказывает единственность причины ECH и не разрешает отключить TLS-защиту. Источники: `docs/ANDROID36_AND_LINKEDIN.md`, `docs/build-info-0.3.2-alpha.json` и `docs/AUTOMATIC_ACCESS.md`.

## Что выполнить в первом новом чате

Если STATE указывает P00 pending, начни P00 и доведи его до конца:

1. **Зафиксируй baseline.** Проверь status/HEAD/ветку и текущие source, untracked work, артефакты и данные. Создай восстановимый checkpoint до удаления файлов. Предпочтительна новая ветка `codex/rebuild-p00` и проверенный commit относящихся source/docs. Проверяй staged diff, не используй `git add .` вслепую, не коммить секреты, ключи подписи, приватные logs, APK и toolchain. Сохрани чужие изменения. Если запись в Git недоступна, сохрани разрешённый локальный snapshot с manifest и объясни ограничение. До очистки production-кода попытайся выполнить подходящий baseline build/test и запиши исходные ошибки среды, чтобы отличить их от новой регрессии.
2. **Повтори аудит по фактам.** Прочитай entry points, lifecycle, настройки/миграции, UI/routes, DNS/hosts, native bridge, patches, engine capabilities, tests, CI, лицензии и provenance. Сравни закреплённые исходники Windows/Mobile и текущий Maffinet; раздели функциональный результат, UX, code inheritance и ограничения платформы. Не делай вывод о неработоспособности всего продукта по одному LinkedIn.
3. **Углуби исследование.** Проверь официальные Android API и RFC, source-built HEV и альтернативный stack, идеи Rethink/Intra/PCAPdroid. Исследуй DNS до TLS, app-owned encrypted DNS, ECH/GREASE, QUIC, original flow tuples/UID, IPv6/NAT64, первый запрос, энергопотребление и TLS identity. Для каждого решения: факт, источник/revision, гипотеза, прототип, цена и acceptance. Не добавляй десятки features без связи с главным сценарием.
4. **Сформулируй самостоятельный продукт.** Запиши пользовательский путь, states/evidence, список функций MVP, расширения и ограничения. Выбор приложения никогда не включает весь телефон; невыбранные приложения не затрагиваются; новое приложение не требует нового hardcoded service toggle. Telegram сохранить независимо и не обещать незаметную установку MTProto proxy в чужом приложении.
5. **Выполни безопасную очистку.** Построй usage/dependency map. Удали подтверждённо ненужные/недостижимые остатки и архивируй отменённые планы с рабочими ссылками. Не удаляй достижимые старые экраны, native и migration до готовой замены. Для них назначь конкретный этап. Очистку фиксируй построчно в `cleanup-ledger.md` с основанием и восстановлением. Сохранение LICENSE/NOTICE/provenance обязательно для сохраняемого кода. Не используй массовую замену названия для сокрытия происхождения.
6. **Окончательно запиши план в `docs/rebuild/`.** Актуализируй аудит, архитектуру, этапы, источники и cleanup. Создай `product.md`, `research.md`, `test-plan.md`, `decisions/`, `sessions/P00.md` и `NEXT_CHAT.md`. Для каждого этапа задай входы, изменяемые области, выходы, проверки, риски и exit criteria. Выбери измеримые SLO после baseline, не копируй 25-секундный host budget как продуктовую цель. Добавь короткий корневой указатель/AGENTS.md на актуальную папку, не затри существующие инструкции.
7. **Проверь результат.** Для документации — paths/links/JSON/diff. Если удалял production/config/build файлы — build и относящиеся проверки. Запиши фактически исполненные команды, коды завершения, skipped и ограничения окружения. Обнови STATE и сохрани локальный commit этапа. Оставь готовый промпт P01 и закончи чат на завершённом P00.

Не ограничивайся предложением плана в ответе: создай файлы, выполни разрешённую очистку, проверки и фиксацию. Не начинай всю реализацию в этом же чате: пользователь хочет последовательные этапы по новым чатам.

Если P00 уже выполнен, не повторяй его. Прочитай STATE/NEXT_CHAT, проверь предыдущий checkpoint и исполни текущий `in_progress` или следующий pending этап. Если состояние расходится с Git/файлами, сначала восстанови фактическую точку продолжения и зафиксируй причину.

## Архитектурные требования для реализации

- Один VpnService и supervisor. Kotlin control plane; bounded native data plane. Прямой независимый adapter к ByeDPI и source-built транспорт. У текущего кастомного HEV и обычного upstream могут различаться JNI и TV-поведение; не подменяй бинарник по похожему имени.
- Source-built transport prototype должен передавать original tuple до SOCKS translation. На API29+ исследуй `ConnectivityManager.getConnectionOwnerUid`; Unknown и shared UID остаются допустимыми. Не подменяй UID приложения UID собственного upstream socket. DNS attribution отдельно и не всегда точна.
- DNS broker должен находиться в реальном пути выбранного трафика. Сначала wire-preserving UDP/TCP forwarding, потом controlled recovery и собственный DoH. A/AAAA/CNAME/HTTPS/SVCB, EDNS, negative TTL, TCP framing/truncation, private DNS и network generations являются контрактами, а не дополнительным декором.
- Все внешние sockets защищены от возвращения в VPN и привязаны к текущей физической сети. Broker и probes закрываются при STOP. Stale decision не устанавливается в новое поколение.
- AccessPlanner выбирает короткий допустимый fallback по наблюдаемому сбою, с deadline/concurrency/backoff и memory сети. Не заставляй пользователя перебирать общий каталог стратегий. Не сканируй массово чужие hostname и DNS providers.
- Не воспроизводи application data, POST, account requests или 0-RTT. Не отключай ECH/сертификаты, не устанавливай CA и не добавляй MITM. Первый безопасный handshake и следующий flow измеряются раздельно.
- QUIC/UDP — отдельная модель. TCP probe не доказывает UDP. Глобальный запрет UDP443 и global AAAA suppression не принимаются как универсальный обход. Fake-IP допускается только как отдельный прототип с проверкой ECH/SVCB/cache/dual-stack.
- Собственный app-first UI, типизированная навигация, ViewModel/StateFlow, versioned repositories и данные. Старые mutable globals и числовые callbacks вывести из production. AppId и совместимую подпись сохраняй, пользовательские настройки мигрируй с backup/report.
- Разделяй engine runtime, DNS/transport evidence, observed flow success и реальные app scenarios. Зеленая кнопка «туннель запущен» не означает «выбранное приложение работает».

Ориентировочные этапы: P00 исследование/очистка/план → P01 transport+helper APK → P02 новый app shell+миграция → P03 supervisor+flow attribution → P04 DNS broker → P05 AccessPlanner+DPI → P06 DoH+mapping → P07 ECH/QUIC/IPv6 acceptance → P08 самостоятельный UI+Telegram → P09 физическая приёмка и удаление активного legacy. Уточняй граф по доказанным зависимостям, сохраняя решения и причины.

## Проверки настоящего результата

Нужен helper APK с другим UID, который выбирается в allowlist и выполняет DNS/TCP/TLS/UDP через реальный TUN. Проба из процесса Maffinet не заменяет эту проверку. Обязательно сравни выбранное и невыбранное приложение, cold/warm запрос, STOP во время recovery, revoke consent, смену Wi-Fi/mobile, process death, фон, IPv6-only/NAT64 и API26/29/36. Native stop/restart и 16 KiB runtime проверяются отдельно.

Реальные app scenarios проверяются на доступном физическом устройстве и сети; учётные данные остаются у пользователя. Лента, API и медиа не выводятся из HTTP200 главной страницы. Если устройство/сеть недоступны, исполни лабораторные проверки, запиши конкретный pending device gate и не объявляй этот gate пройденным.

Текущие базовые команды после проверки toolchain:

```powershell
.\gradlew.bat -p verification test --no-daemon --console=plain
.\gradlew.bat :app:assembleDebug :app:testDebugUnitTest :app:lintDebug -Pmaffinet.ndkVersion=29.0.14206865
```

Для native Linux/Android fixtures и instrumentation используй доступный provisioned host. Не принимай новые SDK соглашения автоматически. После изменения модулей обнови команды; старый test count не является критерием нового продукта.

## Автономность и сохранение работы

Разрешены необходимые локальные reversible изменения, рефакторинг, безопасная очистка проверенных source/doc остатков, сборки, проверки и локальные коммиты этапа. Не запрашивай повторно подтверждение обычного инженерного шага. Если требуется отсутствующая учётная запись, секрет, физическое действие или неразрешённая необратимая операция, объясни конкретную причину; независимую работу продолжай.

Не публикуй, не push, не force push и не merge main автоматически. Не удаляй чужую работу, весь проект или пользовательские данные. Перед рекурсивными Windows move/delete проверь разрешённые абсолютные пути и используй один shell с `-LiteralPath`. Не создавай другие пользовательские чаты или subagents без отдельного разрешения/применимой инструкции.

В конце каждого этапа сохрани `sessions/<stage>.md` с фактическими изменениями, проверками, evidence, limitations и remaining work. Обнови STATE, напиши автономный `NEXT_CHAT.md`, проверь diff, создай локальный commit конкретных файлов и сообщи hash. Если Git заблокирован, явно скажи, что коммита нет, и оставь проверенный snapshot. Не отмечай этап done при невыполненных exit criteria. Не пытайся записать hash ещё не созданного commit в его собственное содержимое.

Финальный ответ каждого чата: выполненный этап, ссылки на результат, commit/checkpoint, что проверено, что осталось и короткий текст для запуска следующего чата. Результат должен быть понятен без предыдущей переписки.

Начинай с чтения файлов и фактического Git status. Выполни текущий этап до конкретного проверяемого результата.
