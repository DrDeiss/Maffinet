# Восстановление сети до TLS: исследование

Дата: 4 октября 2026. Это план следующего инкремента, а не описание реализованной поддержки.

## Что уже есть в коде

`app/src/main/cpp/automatic_access.c` собирает TLS ClientHello из TCP records, извлекает SNI и очищает hostname при любом расширении `0xfe0d`. Таблица маршрутов хранит только `struct in_addr`, порт 443, epoch и срок действия. Observer принимает публичный IPv6, но результат `access_lookup_route` всегда IPv4. `access_tls_replayable` разрешает только handshake/compatibility CCS и отвергает application records, включая 0-RTT.

`HostAccessRecovery.kt` начинает работу с уже наблюдённого адреса, затем проверяет ограниченное число IPv4 DNS-кандидатов с исходным TLS hostname. Поэтому NXDOMAIN, отсутствие ответа DNS и частный sinkhole не запускают восстановление через observer. Это ограничение точки входа, а не нехватка DNS-каталога.

`ByeDpiVpnService.kt` передаёт HEV TUN и SOCKS5-конфигурацию с `udp: udp`, задаёт DNS через `Builder.addDnsServer`, IPv4 default route и опциональный IPv6 default route. Локального DNS listener и `mapdns` в генерируемой конфигурации нет. В репозитории HEV представлен готовыми `.so`: поддержку новых hooks конкретной сборкой следует проверять отдельно. Android `addDnsServer` назначает resolver, но не добавляет контроллер восстановления; без заданного DNS используются серверы default network. [Android API](https://developer.android.com/reference/android/net/VpnService.Builder#addDnsServer(java.net.InetAddress)).

## DNS внутри VPN — приоритетный следующий шаг

Добавить локальный resolver с виртуальным адресом VPN и обработкой UDP **и TCP** 53 до обычного forwarding. Самый ограниченный вариант — направлять к нему системные DNS-запросы через `addDnsServer`; это не перехватывает все запросы к жёстко заданным resolver. Для последних нужен отдельный hook по destination port в SOCKS/TUN пути. Защищать upstream sockets от повторного входа в VPN и привязывать их к физической сети.

Нужна новая модель результата DNS: `positive`, `NXDOMAIN`, `NODATA`, `SERVFAIL`, `timeout`, `truncated`, с RR TTL и SOA для отрицательного кэша. Пустой список IP недостаточен для решения о fallback. NXDOMAIN сам по себе не доказывает блокировку. Ограниченная проверка выбранного и нескольких общедоступных resolver может восстановить ошибочный ответ, но не должна превращать реальный несуществующий домен в произвольный маршрут. NXDOMAIN и NODATA имеют разные ключи кэша; отрицательный TTL определяется SOA. [RFC 2308, §§3–5](https://www.rfc-editor.org/rfc/rfc2308.html#section-5).

Для первого запроса: короткий общий deadline, дедупликация одновременных queries, проверка альтернативного публичного адреса с исходным hostname и обычной проверкой сертификата; только затем ответ приложению. При исчерпании бюджета возвращать корректный DNS-результат, без бесконечного удержания. Сохранять query ID, question, CNAME, EDNS и TCP framing; DNSSEC AD нельзя переносить на синтетически изменённый ответ. Не менять частные/локальные ответы автоматически: это может быть split DNS, а не sinkhole.

Положительный ответ позволяет приложению выполнить **первое** подключение к уже проверенному адресу. Для прямого IP, собственного DoH/DoT/DoQ или ранее закэшированного NXDOMAIN такой гарантии нет. HTTPS/SVCB нельзя бездумно удалять или оставлять от другого endpoint: они задают ALPN, target, port и hints. [RFC 9460](https://www.rfc-editor.org/rfc/rfc9460.html).

## ECH и GREASE

Консервативное исключение сейчас корректно ограничивает ложное обучение. GREASE использует то же расширение и правдоподобные параметры; надёжного универсального распознавания GREASE по одному ClientHello нет. Outer SNI при реальном ECH может быть публичным именем провайдера, а не целевым сервисом. [RFC 9849, §§6.2 и 10](https://www.rfc-editor.org/rfc/rfc9849.html#section-6.2).

Следующий шаг — DNS-восстановление по фактически запрошенному QNAME, независимо от наличия ECH в последующем TLS. Не ослаблять существующий gate только по отсутствию `ech` в одном DNS-ответе: приложение могло закэшировать конфигурацию или получить её иным путём. DNS→IP correlation для общего CDN не доказывает exact hostname конкретного соединения. Не удалять ECH и не отключать проверку сертификатов.

## QUIC / HTTP/3

SOCKS UDP сейчас проходит через `proxy.c` → `udp_hook`; TCP TLS observer этот поток не видит. `ByeDpiArgumentCompiler.kt` в режиме фильтрации по доменам специально ограничивает desync TCP: UDP hook закреплённого движка не учитывает hosts.

DNS-путь поможет и UDP-клиентам, но TCP HTTPS-проба не подтверждает HTTP/3 endpoint. Не применять подтверждённый TCP маршрут автоматически к UDP. Возможен отдельный ограниченный parser QUIC Initial: снять header protection, расшифровать Initial по DCID, собрать CRYPTO fragments и разобрать ClientHello. Initial keys публично выводимы; это не MITM и не расшифровка application data. Потребуются version-specific salts, Retry, packet coalescing и строгие лимиты памяти. ECH всё равно скрывает inner hostname. [RFC 9001, §§4–5](https://www.rfc-editor.org/rfc/rfc9001.html#section-5.2).

Контролируемое прекращение новых QUIC попыток может вызвать TCP fallback у HTTP-клиента: стандарт рекомендует такой fallback при проблемах UDP, но не гарантирует его каждому приложению. Не включать глобальную блокировку UDP 443: там возможен другой протокол, а HTTP/3 бывает на других портах. Первым шагом считать диагностику QUIC и испытание ограниченной политики на тестовых клиентах. [RFC 9114, §3.1](https://www.rfc-editor.org/rfc/rfc9114.html#section-3.1).

## IPv6 и безопасное первое подключение

Расширить DNS-модель A/AAAA и route storage до family-aware адреса, отдельно подтверждать каждый кандидат. Учитывать NAT64/DNS64 и IPv6-only физическую сеть: принудительный IPv4 может быть недоступен. Не подавлять AAAA глобально. Пробы семей запускать со сдвигом и единым бюджетом, без ожидания всех DNS-ответов. [RFC 8305, §§3–7](https://www.rfc-editor.org/rfc/rfc8305.html).

Для TCP после ClientHello можно исследовать ограниченное удержание handshake до выбора подтверждённого маршрута; интеграция должна явно передать решение в native flow. Нынешняя асинхронная таблица прежде всего помогает следующим подключениям. Сохранять запрет повторения после application data, 0-RTT или ответа сервера; plain HTTP автоматически не воспроизводить. Epoch/STOP/смена сети должны отменять и DNS, и ожидание handshake.

## Проверка перед выпуском

Нужны сценарии реального NXDOMAIN и подменённого ответа, NODATA, UDP truncation→TCP, CNAME/HTTPS/EDNS, легального private DNS, ECH и GREASE, QUIC с/без TCP fallback, IPv6-only/NAT64, смены сети, STOP и 0-RTT. Измерять успех первого запроса и задержку отдельно от успеха следующего соединения. Не заявлять per-app attribution без UID hook HEV.

Upstream HEV описывает `mapdns`, но его наличие в текущих бинарниках и пригодность для такого recovery не установлены; fake-IP требует специального обхода нынешнего public-address gate и безопасной передачи hostname, поэтому не является простой заменой локального resolver. [HEV README](https://github.com/heiher/hev-socks5-tunnel#configuration).

DNS и локальный DPI не меняют внешний IP. Без доступного общедоступного альтернативного endpoint полную IP/GeoIP-блокировку гарантированно устранить нельзя.

## Следующий кодовый этап после физической проверки 0.3.2

В `byedpi/proxy.c` точки до `connect` в `on_udp_tunnel` и до `connect_hook` в
`handle_s5` позволяют направлять только UDP/TCP53 к выбранным DNS в локальный
асинхронный forwarder, сохраняя предпочтения и назначения VPN. UDP-ответ должен
возвращать исходный адрес DNS в SOCKS header, а не адрес локального listener.
Обычные ответы нужно переносить исходными wire bytes; нынешний A-only
`DnsProbeResolver` не заменяет полноценный forwarder и не сохраняет все RR/TTL.
Worker должен привязывать upstream sockets к физической Network и закрываться
при STOP/смене поколения. Нужны отдельные тесты UDP source address, TCP framing,
CNAME/EDNS/HTTPS/AAAA, private ответов, отмены и ограничений очереди.

Этот перехват не охватит системный Private DNS или собственный DoH приложения.
На телефоне Private DNS оставался активным; в native metadata наблюдались TCP853
соединения, но конкретные DNS queries внутри TLS не читались. Поэтому нельзя
выдавать plaintext DNS forwarder за уже найденное исправление сбоя LinkedIn.
Успешная TLS443-проба также не разрешает автоматически подменять DNS для всех
портов/UDP. Политика recovery и согласование A/AAAA/HTTPS требуют отдельной
реализации; штатный NXDOMAIN выбранного фильтрующего DNS не является достаточным
основанием обходить пользовательский выбор.
