# Автоматический доступ

## Исправление контрольной пробы — 0.3.2-alpha

Проверка на OnePlus выявила ошибку 0.3.1: `example.com` отвергался существующим
фильтром публичных hostname до TLS. DNS возвращал адреса, но TLS-проверка вообще
не начиналась (`Invalid public HTTPS host`). Это была ошибка диагностики, а не
доказательство неисправности выбранного GeoHide. Контрольный hostname заменён
единой константой `www.iana.org`, проходящей тот же production-фильтр; регрессия
проверяет этот контракт без доступа в Интернет. Причина HTTPS-ошибки теперь
показывается рядом с результатом. Проверка сертификатов и фильтр не ослаблены.

Auto 0.3.1 на телефоне подтвердил маршрут `www.linkedin.com → 130.211.32.14`.
Отдельный анонимный запрос через телефон к исходному адресу `104.18.41.41`
с обычным SNI получил по Auto полный HTTP200, 140059 байт тела за 656 мс.
Однако само приложение LinkedIn после холодного старта оставалось на загрузке;
его native-соединения всё ещё шли на исходные адреса. Это не считается успешной
приёмкой LinkedIn. В 0.3.2 добавлена диагностическая запись только о наличии
ECH-расширения (включая возможный GREASE), без содержимого TLS/запросов, чтобы
проверить эту причину на реальном ClientHello. Политика ECH не изменена.

## DNS-конфигурация: следующий инкремент 0.3.1-alpha

Состояние DNS разделяет сохранённый выбор, адреса, переданные Builder действующего
VPN, DNS физической сети и активность/имя системного Private DNS. Собственный
DoH/DoT приложений и фактический resolver их запросов остаются неизвестными.
При несовпадении сохранённого выбора и назначения VPN интерфейс просит
переподключиться; настройки не переписываются автоматически.

Контекст проверок включает все эти назначения, адреса интерфейса и маршруты
физической сети. Монитор проверяет изменения каждые 500 мс, в работающей пробе —
до 250 мс между операциями. Новое поколение отменяет старую очередь, очищает
native-маршруты и отделяет результаты от прежней конфигурации. Блокирующий TLS
вызов может завершиться позже, но результат отменённого поколения не публикуется.

После запуска и изменений выполняется ограниченная контрольная проверка
`example.com`: прямой обычный DNS к выбранным IPv4 resolver (или DNS сети при
наследовании), затем HTTPS по первому публичному адресу с исходным hostname,
проверкой сертификата и до 64 КиБ тела. Максимум четыре resolver, до двух секунд
на DNS и трёх на HTTPS каждого. Она не устанавливает маршрутов и не подтверждает
работу всех сервисов. Для проверяемых при восстановлении доменов результаты
выбранного DNS также видны отдельно от найденного маршрута.

DNS различает ANSWER, NODATA, NXDOMAIN, RCODE, некорректный ответ, таймаут и ошибку
транспорта. Непубличные ответы сохраняются как возможные заглушки без утверждения
о блокировке. Публичную заглушку нельзя надёжно узнать только по IP; TLS/HTTP-проба
отдельно проверяет доступность. Законный NXDOMAIN, отсутствие A у IPv6-only
домена и HTTP-отказ не объявляются доказанной блокировкой. Проверяются UDP и TCP
при усечённом UDP-ответе; проверки DoT/DoH и перехват DNS выбранных приложений
ещё не реализованы. Эти DNS-пробы идут напрямую по физической сети, а не через
VPN/HEV; это явно отличается от доказательства пути запросов приложения.

Дальнейшие варианты DNS до TLS, ECH/GREASE, QUIC, IPv6 и первого соединения
исследованы в [NETWORK_RECOVERY_RESEARCH.md](NETWORK_RECOVERY_RESEARCH.md).
Исходники `f596fe9` прошли [CI 37205002273](https://github.com/DrDeiss/Maffinet/actions/runs/37205002273):
158 standalone JVM/native-parser, 156 Android JVM, native socket и sanitizer
проверки, сборку и эмуляторы Android10/16. Подписанный APK 0.3.1-alpha сохранён
локально с прежним сертификатом. [Метаданные](build-info-0.3.1-alpha.json)
фиксируют точный объём проверки. ADB повторно потерял связь до установки;
приёмка Auto на физическом OnePlus остаётся открытой.

Уточнение пользователя от 4 октября 2026: LinkedIn был примером недостатка
классического обхода. Основной сценарий Maffinet — выбрать приложения и нажать
«Подключиться». Отдельные переключатели для каждого сервиса не нужны.
Допустимы локальный DPI-обход и общедоступные Smart DNS; собственного внешнего
VPN/прокси-сервера в этой архитектуре нет.

## Общий механизм

1. Android VpnService сохраняет явный список выбранных приложений. Автоматический
   режим охватывает видимые TLS hostname их трафика, включая имена вне General.
   General/User и сохранённые команды остаются настройками ручного режима.
2. Короткая цепь TLS-стратегий запускается сразу; полный перебор 73 рецептов и
   трёх заранее заданных сайтов не задерживает обычное подключение. Plain HTTP
   и неизвестные протоколы не получают повторения прикладных запросов. После
   полного TLS ClientHello отсутствие ответа в течение двух секунд разрешает
   следующую попытку только до передачи прикладных данных. После начала TLS
   application data, включая 0-RTT, такой повтор запрещён.
3. Native observer передаёт hostname, порт и исходный адрес в ограниченную очередь.
   Kotlin-проверки работают отдельно от сетевого цикла. Никакие cookies,
   Authorization или содержимое запросов приложения в проверки не копируются.
   Наблюдение и перенаправление ограничены публичными адресами TCP 443. Локальный
   HTTPS, неполный или некорректный ClientHello проходят без новой TLS-стратегии.
4. Контроллер проверяет соединение с исходным TLS hostname и сертификатом,
   читая 64 КиБ ответа или полный меньший ответ. HTTP-код сохраняется отдельно:
   законные 401/403/404 на публичном `/` API не означают доказанную блокировку.
5. При неполной передаче проверяются IPv4-ответы выбранного DNS и ограниченного
   набора Smart DNS. DNS запрашивается прямо у указанного resolver; системный
   `getaddrinfo` не подменяется тестом выбранного VPN DNS.
6. Каталог RouteHint содержит данные об известных допустимых endpoint. LinkedIn
   является первой записью; механизм не имеет отдельного LinkedIn режима.
   Новый неизвестный hostname также проходит DNS/DPI проверки без изменения UI.
7. Только подтверждённый вариант устанавливается в exact-host/port таблицу.
   Новые соединения получают его без перезапуска VPN или разрыва других потоков.
   Внутренние пробы обходят эту таблицу, чтобы измерять настоящий адрес кандидата.
8. Решения ограничены TTL и контекстом физической сети. STOP и смена поколения
   отменяют публикацию старых результатов. Первый инкремент хранит ограниченный
   кэш в процессе; успешный результат не считается бессрочным свойством домена.
   Периодический монитор проверяет изменения сети и DNS также при пустой очереди;
   обновление контроллера не требует перезапуска VPN. TTL учитывает сон устройства.
   Прямая доступность одного IP не считается доказательством для остальных IP
   того же домена. Сохранённый альтернативный маршрут действует до десяти минут.

## Область действия

Механизм включён по умолчанию в 0.3.0-alpha. Для исходников
`8266a409f085a6e1050a5d54400ff199cb1de207`
[CI 37199682071](https://github.com/DrDeiss/Maffinet/actions/runs/37199682071)
прошёл native/JVM-проверки, ASan/UBSan/leak check, сборку и сценарии Android 10/16.
Приёмка нового автоматического режима на телефоне остаётся открытой: ADB-связь
потеряна. Успешная ручная диагностическая команда LinkedIn подтверждает один
кандидат, но не работу автоматического режима на этом устройстве.

DNS/desync сами по себе не меняют внешний IP. Smart DNS помогает сервисам,
которые конкретный поставщик действительно ретранслирует. Полную IP-блокировку,
недоступность самого сервера, ограничения аккаунта или произвольную GeoIP-политику
без доступного альтернативного маршрута гарантированно устранить невозможно.

TLS остаётся непрозрачным: наблюдение hostname не раскрывает статус авторизованного
API и не подтверждает все функции приложения. Уже установленный TLS поток
не переносится на другой сервер; выбранный вариант используется для следующих
подключений, повтор выполняет приложение. Шифрованный SNI/ECH и QUIC требуют
отдельных механизмов; текущий инкремент не заявляет их универсальный обход.
ClientHello с расширением ECH консервативно исключается из обучения маршрутов,
включая GREASE ECH. Обычный локальный DPI-обход остаётся доступен, но Smart DNS
восстановление через этот observer для такого соединения не запускается.

Первый инкремент запускает восстановление после наблюдения TLS hostname.
Если DNS вообще не вернул адрес, ответил частным адресом блокировки либо
приложение использует собственный скрытый DNS/hostname, наблюдения может не быть.
Перехват и восстановление всех DNS-запросов VPN пока не реализованы; расширенный
каталог DNS и проверки кандидатов не равнозначны такому перехвату.

HEV не отдаёт Kotlin исходный 5-tuple/UID. Поэтому состояние показывается для
выбранного набора и проверенных hostname, без выдуманной точной per-app телеметрии.
Клиент видит состояние подключения и автоматической проверки; недоступность после
исчерпания вариантов должна оставаться видимой.
