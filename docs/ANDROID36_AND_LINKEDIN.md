# Android 16 и проверка LinkedIn

Отзыв о сборке 0.1.0-alpha: системное предупреждение об устаревшем Android,
LinkedIn не открывается ни в приложении, ни в браузере; остальные сервисы работают.
Выбран GeoHide. Пользователь удалил приложение и предложил подключить телефон по
USB для проверки на своей сети.

## Подтверждено и изменено

- `targetSdk=26` действительно оставался в APK. В 0.2.0-alpha установлен target36;
  min26 сохраняет поддержку Android8. Исправлены связанные изменения поведения:
  разрешение уведомлений, запуск из плитки через PendingIntent, восстановление
  запрошенного подключения при возвращении на экран и обработка обновления из фона.
- JNA 5.14.0 имела подтверждённую проблему 16KB. Используется официальный AAR 5.19.1
  (SHA-256 `b57125cb7d16253f0d65a80f7d3a4c3664effa711b8bdbb7f87fb572ce1624ed`).
  Совместимость используемых Java API проверена. Остальные native-бинарники
  сохранены; полная сертификация APK для 16KB-устройств не заявляется.
- Автоподбор мог применить стратегию при успехе 2/3 сайтов, включая неудачу LinkedIn.
  Теперь автоматическое применение требует успеха всех заданных URL. При
  частичном результате прежняя команда и режим сохраняются; ошибки видны в
  карточках и итоговом сообщении. Частичную стратегию можно выбрать вручную.
- Первый запуск теперь направляет к существующему выбору приложений на главном
  экране и напоминает добавить браузер для проверки сайтов. Удалена подсказка
  о несуществующем экране «Сервисы». Диагностический отчёт показывает реально
  скомпилированные аргументы обхода, скрывая содержимое пользовательских hosts.

## Что пока не доказано

`linkedin.com` и `licdn.com` уже присутствуют в General. Native-сопоставление
покрывает их поддомены. Добавление `www` или `api` не является исправлением.
Опубликованные конфигурации GeoHide не содержат проксирования LinkedIn.
UDP/QUIC по-прежнему передаётся без выборочного desync.

Одни заголовки HTTP200–399 не доказывают доступность ответа, всех API и медиа.
В этой сети два Cloudflare-адреса LinkedIn отвечают HTTP200, но не завершают
загрузку тела. Найден и проверен отдельный endpoint самого LinkedIn, через
который браузер и приложение работают; подробности приведены ниже.

## Проверка на физическом телефоне, 4 октября 2026

OnePlus 15: Android 16 / API36, размер страницы памяти 4096 байт. На старом APK
с target26 воспроизведено системное предупреждение об устаревшем приложении;
на новом APK с target36 это предупреждение отсутствует. Этот телефон проверяет
работу с 4KB-страницами и не подтверждает полную совместимость с 16KB.

Полный автоподбор проверил 73 кандидата: 219 HTTP-проб по трём адресам:

| Проверочный сайт | Успех | Неудача |
| --- | --- | --- |
| YouTube | 16/73, HTTP302 | 56 таймаутов чтения и 1 `timeout` |
| LinkedIn | 55/73, HTTP200 | 18 таймаутов чтения |
| Instagram | 0/73 | 73 таймаута соединения |

Ошибок `SOCKS: Host unreachable` в новом прогоне нет. Native-лог содержит
219 успешных разрешений имени с последующим созданием исходящего соединения.
Массовые мгновенные отказы старого прогона не воспроизвелись; их причина не
установлена. Ни один кандидат не прошёл все три адреса. По завершении проверки
сохранены прежняя ручная стратегия и ручной режим; UI показывал частичный
результат 2/3 без автоматического применения новой команды.

В Android системный Private DNS остался `xbox-dns.ru`; в Maffinet выбран
GeoHideRU. При автоподборе VPN остановлен: HTTP-пробы идут через локальный
SOCKS, а native `getaddrinfo` использует системное разрешение имён Android.
Поэтому эти пробы проверяют системный DNS, а не выбранный DNS работающего VPN.

Отдельные TLS-пробы через телефон показали зависимость от размера ClientHello:
валидный Hello размером 517 байт успешно устанавливает TLS с LinkedIn при
`-d1 -r1+s`; увеличенные Hello размером 1300–2020 байт не получают ответа.
Добавление TCP-разбиения и ожидания между частями:

```text
-d1 -s1+s -r1+s -Z -W20 -R1
```

позволило установить TLS в прямых пробах с Hello размером 2020 байт и с
ClientHello с PQC размером 1541 байт. Одного изменения разбиения недостаточно:
браузер и приложение на исходных адресах всё ещё не завершали загрузку.

## Полная загрузка и рабочий маршрут LinkedIn

Проверка GET без cookies и авторизации, с `Accept-Encoding: identity`, отдельно
измерила весь HTTP-ответ через SOCKS на телефоне. Для обоих адресов
`104.18.41.41` и `172.64.146.215` получены HTTP200 и 13 781 байт тела
(19 166 байт вместе с заголовками), затем таймаут. Chunked-ответ не завершён.
Chrome также показывал HTTP200 по h2, но не завершал загрузку документа;
отдельный CSS-файл по h3 загрузился полностью. Это подтверждает обрыв передачи
после успешного начала соединения, а не успешную доступность сайта.

У LinkedIn обнаружен действующий DNS endpoint `gcp-lb.www.linkedin.com`.
Его адрес подтверждён независимым DNS-запросом; соединение с исходным SNI
`www.linkedin.com` проходит обычную проверку сертификата. Через этот endpoint
на телефоне полностью загружен HTTP200: 140 059 байт тела, совпадающих с
Content-Length, за 766 мс.

В диагностической стратегии перенаправлялся только TLS-трафик порта443 для
`www.linkedin.com`; остальные hostname оставались в отдельной группе.
С разбиением `-d1 -s1+s -r1+s -Z -W20 -R1` загрузились лента и изображения
в настоящем приложении LinkedIn и лента в Chrome. Повтор после остановки и
запуска VPN и холодного запуска LinkedIn также прошёл. Сообщения, публикации
и другие действия с учётной записью не проверялись.

Этот результат подтверждён диагностической командой на данной сети и устройстве;
работоспособность endpoint в других сетях и всех функций LinkedIn требует
отдельной проверки. Новый общий автоматический режим ещё не проверен на телефоне.

## Общий автоматический режим и критерий HTTP-проверки

Пользователь уточнил требование: LinkedIn служит примером, а основной сценарий
должен работать для выбранных приложений без отдельных переключателей сервисов.
Поэтому прежний экспериментальный профиль заменён общим [автоматическим
режимом доступа](AUTOMATIC_ACCESS.md). Сохранённая ручная команда и Hosts остаются
доступны в экспертном режиме.

Для каждого наблюдаемого публичного TLS hostname контроллер проверяет исходное
соединение, затем при необходимости ограниченный набор DNS/Smart DNS ответов.
`gcp-lb.www.linkedin.com` стал первой записью в каталоге допустимых endpoint,
без фиксированного IP и исключения из проверки сертификата. Неизвестный домен
также проходит общий алгоритм, даже если отсутствует в General.

Подтверждённый адрес применяется только к новым соединениям соответствующего
hostname и порта, с TTL и привязкой к физической сети. Установленные TLS потоки
и авторизованные запросы приложения не воспроизводятся. Первому неудачному
соединению может потребоваться повтор со стороны приложения. В UI показывается
состояние автоматической проверки, а не обещание доступности всех функций.
При остановке и смене поколения старые проверки теряют право публиковать маршрут.

HTTP 200–399 теперь недостаточно для успеха ответа с телом: проверка
загружает первые 64 КиБ либо весь меньший ответ до EOF. При известном Content-Length
преждевременный EOF до проверяемого объёма считается ошибкой. Зависшее чтение
ограничено socket read timeout 2,5 с; общий предел чтения между вызовами также
отсекает медленную непрерывную передачу. Отмена проверяется перед и после
чтения; уже заблокированное чтение может ждать до read timeout.

HTTP 204/205, явно пустое тело и редиректы сохраняют допустимую семантику без
обязательной загрузки тела. Крупный ответ проверяется только до 64 КиБ, а
редирект не прослеживается до конечного сайта. Поэтому успех не удостоверяет
полную загрузку крупного документа, аутентификацию, API или медиа. HTTP-код и
ошибка тела видны вместе в деталях матрицы. Версия fingerprint обновлена:
старые результаты, проверявшие только заголовки, больше не считаются актуальными.

При более сложном paced-разбиении журнал также показал повторную вставку
TLS-заголовка в тот же ещё отправляемый buffer после получения ответа сервера.
Это отдельная воспроизведённая ошибка native-обработки; исправление проверяется
на повторный вход, неполную отправку, ожидание таймера и сохранение данных. Она не объясняет ограничение
объёма HTTP-ответов на двух исходных адресах.

Контекст сетевого ограничения:
[Cloudflare о нарушении доступности в России](https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet/).
Сходство с описанным ограничением около16КБ является выводом из измерений;
конкретное оборудование или правило оператора на этой сети не установлены.

## Проверка

Исторический локальный прогон до перехода к общему режиму: 90 JVM-тестов
зарегистрировано, 84 прошли, 6 native-контрактов ожидаемо пропущены на Windows.
Он включал прежний профиль LinkedIn и не считается проверкой нового алгоритма.
Для общего режима добавлены отдельные проверки неизвестных hostname, TTL,
сетевого контекста, отмены и подтверждения альтернативного адреса.
CI собирает один app/test APK pair,
затем запускает его на API29 и API36; современный сценарий проверяет реальный
VPN/SOCKS/Telegram при разрешённых и запрещённых уведомлениях. Результаты
нового общего режима ожидаются; данные физического телефона выше относятся
к диагностической ручной команде.
